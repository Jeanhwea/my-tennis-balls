# Comment Style Guide

## 1. Overview

This guide is compiled based on the existing comment style of the my-tennis-balls project and applies to all C++ source files (.h, .hpp, .cpp) in the project.

---

## 2. Comment Types and Formats

### 2.1 File Header Comment - `/// @file`

Used at the top of header files to describe the purpose of the file.

**Format:**

```cpp
/// @file <filename>
/// <file description>
```

**Examples:** (from `GameConstants.h`, `BallView.h`)

```cpp
/// @file GameConstants.h
/// Global constants: tags, masks, physics parameters, layout ratios, scoring rules.
```

```cpp
/// @file BallView.h
/// Creation and removal animations for ball sprites.
```

---

### 2.2 Class/Struct/Namespace Comment - `///`

Used before class and struct definitions, or after namespace declarations, with `///` to describe purpose.

**Format:**

```cpp
/// <class/struct/namespace description>
class ClassName { ... };
```

**Examples:** (from `GameController.h`, `GameModel.h`, `InputController.h`)

```cpp
/// Coordinates Model <-> View communication, level progression, and physics system.
class GameController { ... };
```

```cpp
/// Core game state, pure data with no rendering.
class GameModel { ... };
```

```cpp
/// Handles touch input, converts drag gestures into launch commands.
class InputController { ... };
```

```cpp
/// Creates physics boundary walls, floor sensors, and zone visual effects.
namespace ArenaView { ... };
```

---

### 2.3 Function/Method Comment - `///`

Method declarations in header files use `///` comments to describe functionality.

**Format:**

```cpp
/// <function description>
/// @param <parameter name> <parameter description>
/// @return <return value description>
return_type functionName(parameters);
```

**Examples:** (from `InputController.h`, `TrayView.h`, `VFXHelper.h`)

```cpp
/// Registers touch event listeners on the specified node.
void init(cocos2d::Node *target);
```

```cpp
/// Creates all trays and target balls in the level.
/// @param outTargets Output parameter, stores the created target ball node pointers
/// @return Total number of target balls
int createFromLevel(cocos2d::Node *parent, const cocos2d::Size &visibleSize,
                    const LevelData &level,
                    cocos2d::Vector<cocos2d::Node *> &outTargets);
```

```cpp
/// Initializes the particle pool, pre-allocates DrawNode objects to avoid runtime allocation overhead.
/// @param parent Parent node of the particle pool node
/// @param poolSize Pool size, default 50
void initParticlePool(cocos2d::Node *parent, int poolSize = 50);
```

---

### 2.4 Struct Field Comment - `///<` (Trailing Comment)

Add descriptions at the end of struct field definition lines using `///<`.

**Format:**

```cpp
<type> <field_name>;  ///< <field description>
```

**Examples:** (from `LevelData.h`)

```cpp
struct TrayData {
    float x;      ///< Center X (screen width ratio 0~1)
    float y;      ///< Center Y (screen height ratio 0~1)
    float width;  ///< Width (screen width ratio 0~1)
    int targets;  ///< Number of target balls on this tray
};

struct LevelData {
    int id;
    std::string name;
    int maxBalls;                 ///< Maximum number of launchable balls allowed
    std::vector<TrayData> trays;  ///< Tray configurations
};
```

---

### 2.5 Code Section Comment - `//`

In `.cpp` files, use `//` comments to describe the purpose of a block of code. Suitable for important logic blocks inside functions.

**Format:**

```cpp
    // <description text>
    // <detailed description (if needed)>
    code...
```

**Examples:** (from `LevelData.cpp`, `InputController.cpp`)

```cpp
    // Check for JSON parse errors
    if (doc.HasParseError()) { ... }
```

```cpp
    // Only effective for touches within the launch area (right-side LAUNCH zone)
    auto pos = touch->getLocation();
```

---

### 2.6 Multi-line Description Comment - `///`

Before functions or complex logic, use consecutive `///` lines for detailed explanation.

**Format:**

```cpp
    /// <First line overview>
    /// <Subsequent detailed explanation>
```

**Example:** (from `BallView.cpp`)

```cpp
    /// Synchronously updates the highlight position with ball rotation, simulating the
    /// sliding of a reflection point on the ball surface under a fixed light source.
    /// Core idea: the highlight is an independent node; its position on the ball surface
    /// is calculated by rotating the light direction vector.
    if (!ball) return;
```

---

### 2.7 Grouped Constants/Variables Comment - `// --`

Before constant definitions or member variable groups, use `// -- <title> --` for grouping markers.

**Format:**

```cpp
// -- <group title> --
constexpr int GROUP_CONSTANT_1 = ...;
constexpr int GROUP_CONSTANT_2 = ...;
```

**Examples:** (from `GameConstants.h`)

```cpp
// -- Fonts --
constexpr const char *FONT_UI = "fonts/arial.ttf";
// -- Node Tags --
constexpr int TAG_BALL = 100;
// -- Collision Category Masks --
constexpr int CATEGORY_BALL = 0x01;
// -- Global Physics --
constexpr float GRAVITY_Y = -980.0f;
// -- Ball --
constexpr float BALL_SCALE = 0.22f;
// -- Ball Lighting Effects --
constexpr float BALL_SHADOW_OFFSET_Y = -8.0f;  ///< Shadow Y offset
```

**Also used for function grouping:** (from `GameController.h`)

```cpp
// -- Level --
void loadLevel(...);

// -- Input & Physics --
void setupInput();

// -- Ball Management --
void spawnBall(...);

// -- Collision --
bool onContactBegin(...);
```

---

### 2.8 Code Logic Section Comment - `// --`

Use `// --` inside functions to separate logical sections.

**Format:**

```cpp
// -- Section Title --
```

**Example:** (from `BallView.cpp`)

```cpp
    // -- Lighting System --
    // The highlight and secondary highlight are independent nodes, not children of the ball,
    // to simulate a fixed light source in world space.
    // As the ball rotates, the highlight slides across the ball surface (calculated in updateHighlights)

    // Main highlight: white highlight on the upper-left of the ball (simulating main light source)
    auto highlight = Sprite::create("ball.png");
```

---

### 2.9 Namespace Closing Marker - `}  // namespace`

Add a comment after the closing brace of a namespace for readability.

**Format:**

```cpp
}  // namespace <namespace name>
```

**Examples:** (from `BallView.h`, `LevelData.cpp`)

```cpp
}  // namespace BallView

#endif  // __BALL_VIEW_H__
```

```cpp
}  // namespace
```

---

### 2.10 Branch/Loop/Condition Comment - `//`

Used to explain the intent of a branch condition in code.

**Format:**

```cpp
    // <condition description>
    if (...) {
```

**Examples:** (from `VFXHelper.cpp`)

```cpp
    // Pool exhausted, create temporary node (will be destroyed after use)
    auto node = DrawNode::create();
```

```cpp
    // Pool exhausted, create temporary label (will be destroyed after use)
    auto label = Label::createWithTTF("", FONT_TITLE, FLOAT_SCORE_FONT);
```

---

### 2.11 Key Requirement / Design Decision Comment - `//`

Used to mark non-obvious constraints, requirements, or design decisions.

**Format:**

```cpp
    // <requirement description> (Requirement <version>)
```

**Examples:** (from `VFXHelper.cpp`)

```cpp
    // Maximum active particles cap (Requirement 2.3)
    // spawnHitParticle uses 15 nodes: 12 particles + 2 rings + 1 flash
    static constexpr int PARTICLES_PER_HIT = 15;
```

```cpp
    // Check particle count cap (Requirement 2.3)
    // Reject spawn if adding 15 particles would exceed maximum
    if (g_particlePool.initialized && ...) { return; }
```

## 3. Comment Language

Project comments are written in **English**.

## 4. Comment Style Selection Guide

| Scenario | Comment Format | Location |
|----------|----------------|----------|
| File description | `/// @file` | Top of .h file |
| Class/struct/namespace description | `///` | Before definition |
| Function declaration description | `///` + `@param`/`@return` | In .h file |
| Struct field description | `///<` | In .h file, after field |
| Multi-line description inside function | `///` | In .cpp, before code |
| Single-line description inside function | `//` | In .cpp, before code |
| Logic section separation | `// --` | In .h / .cpp |
| Branch/loop condition description | `//` | In .cpp, before branch/loop |
| Requirement/design decision marker | `//` | In .cpp, before relevant code |
| Namespace closing | `} // namespace` | At namespace closing brace |

## 5. Notes

- Comments should be updated in sync with code; outdated or incorrect comments are worse than no comments.
- Avoid obvious comments (e.g., `int i; // counter`), comments should explain WHY, not WHAT.
    - Bad: `i++; // increment i` (redundant)
    - Good: `i++; // skip processed tasks` (explains business meaning)
- `///` comments in function declarations use present tense, imperative mood.
- In-code `//` comments use English, `///` documentation comments also use English.
- Commented-out dead code should be deleted directly. If retention for reference is needed, the reason and deletion timeline should be noted.

---

## 6. Notes on Language Usage

- `/// @file` header comments: Use English
- `///` documentation comments: Use English
- `///<` trailing comments: Use English
- `// --` section titles: Use English
- `//` in-code comments: Use English
