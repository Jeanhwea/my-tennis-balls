# my-tennis-balls 重构分析

## 1. 概览

本文档基于对 my-tennis-balls 项目全部源代码的交叉审阅，识别现有架构中的设计问题、代码坏味和可优化点，并给出具体的重构建议。

项目规模：约 3300 行 C++（.h + .cpp），34 个源文件，基于 cocos2d-x v3 引擎，采用 MVC + Mediator 模式。

---

## 2. 现有架构回顾

### 2.1 模块划分

```
AppDelegate
  └─ LevelMenuScene             关卡选择（静态 s_initialPage）
       └─ GameScene (composition)
            └─ GameController    核心中介者（值成员持有）
                 ├─ GameModel        纯数据状态容器
                 │    └─ ScoreManager  计分/连击逻辑
                 ├─ InputController  触摸输入（回调驱动）
                 ├─ AimLineView      瞄准线渲染
                 ├─ HUD              抬头显示（cocos2d::Node 子类）
                 └─ ArenaView / BallView / TrayView / ObstacleView / VFXHelper
                       （多为无状态命名空间工厂函数）
```

### 2.2 当前模式总结

- **Model** 层纯 C++ 无渲染依赖，值得肯定
- **View** 层以命名空间自由函数为主，组合灵活
- **Controller** 作为唯一中介者承上启下
- **回调驱动** 通信（`std::function`）替代继承或事件总线

## 3. 主要设计问题

### 3.1 GameController 过度膨胀（God Class）

**问题：** `GameController` 目前承担了以下全部职责：

- 关卡生命周期管理（`loadLevel` / `clearLevelNodes` / `onLevelCleared` / `onLevelFailed`）
- 碰撞回调分发（`onContactBegin` 及三个子处理函数）
- 球体和目标的创建与销毁（`spawnBall` / `removeBall` / `removeTarget`）
- VFX 触发（浮动分数、粒子效果）
- HUD 联动（`refreshHUD`）
- 物理系统初始化
- 输入系统初始化
- 延迟移除管理

单文件 327 行，头文件声明 25 个函数/方法（不算 getter/setter）。随着功能增长，这个数字将继续膨胀。

**影响：** 可测试性差、职责混杂、修改一处容易影响另一处。

### 3.2 GameModel 贫血模型

**问题：** `GameModel` 本质上是一个结构体 + getter/setter，没有任何行为逻辑：

```cpp
class GameModel {
    int _ballCount = 0;      // 仅 set/get
    int _targetsRemaining = 0;  // 仅 set/get
    int _levelIndex = 0;     // 仅 set/get
};
```

所有业务判断（如 `isCleared`、`hasNextLevel`、`currentLevel`）虽然写在 GameModel 中，但真正的"行为"——何时增减 ballCount、何时修改 targetsRemaining——全部在 `GameController` 中。

**影响：** 业务规则散落在 Controller 中，无法独立测试模型逻辑。

### 3.3 VFXHelper 全局可变单例

**问题：** `VFXHelper` 使用文件作用域的全局静态变量管理对象池：

```cpp
// VFXHelper.cpp
ParticlePool g_particlePool;   // 全局静态
LabelPool g_labelPool;         // 全局静态
```

这些池在 `initParticlePool` 时初始化，但在场景销毁时从未清理。如果场景反复创建/销毁（比如玩家反复进入退出关卡），池中积累的 `DrawNode` / `Label` 节点仍然挂在已经销毁的 parent 上，导致悬挂指针。

**影响：** 潜在的内存安全问题，长时间游戏后可能崩溃。

### 3.4 得分倍率逻辑重复

**问题：** `ScoreManager::addScore` 内部已经做了连击倍率计算：

```cpp
void ScoreManager::addScore(int basePoints) {
    _score += basePoints * std::max(1, _combo);  // 这里乘了 combo
    _combo++;
    ...
}
```

但在 `GameController` 的匿名命名空间中，`applyScoreVFX` 又做了一次：

```cpp
void applyScoreVFX(...) {
    int points = basePoints * std::max(1, score.combo());  // 又乘了一次
    score.addScore(basePoints);  // 这里内部又乘一次
    ...
}
```

结果是每次碰撞得分被乘以了两次 combo。

**等等——重新看代码：** `addScore` 确实将 combo 计入总分，而 `applyScoreVFX` 在调用 `addScore` 之前又算了一个 `points` 用于显示。也就是说 `addScore` 内部的 score 是对的（`score += base * combo`），但显示的 `points` 是 `base * combo`，和实际加的分一致。**实际上没有 bug**，但逻辑上令人困惑——`applyScoreVFX` 的 `points` 计算重复了 `addScore` 的倍率逻辑，应当只算一次，由 `addScore` 内部决定最终分值，VFX 只需要显示结果。

### 3.5 HUD 在父节点上创建子节点

**问题：** `HUD::showCleared()`、`showFailed()`、`showLevelIntro()` 都调用 `getParent()->addChild()` 来添加动画节点：

```cpp
void HUD::showCleared() {
    auto flash = DrawNode::create();
    // ...
    getParent()->addChild(flash, 29);   // HUD 假设父节点存在
    auto cleared = Label::createWithTTF("ALL CLEAR!", ...);
    // ...
    getParent()->addChild(cleared, 30); // 绕过自身节点层级
}
```

**影响：** HUD 的布局逻辑依赖外部（父节点），破坏了封装。如果 `getParent()` 返回 nullptr（节点未加入场景树时调用）或父节点类型不符合预期，将直接崩溃。

### 3.6 重复的视觉绘制代码

**问题：** 背景渐变、网格线、角落装饰等绘制逻辑在以下文件中重复出现：

| 绘制内容 | 出现位置 |
|---------|---------|
| 垂直条纹背景渐变 | `ArenaView.cpp` (第 74-89 行)、`LevelMenuScene.cpp` (第 44-54 行) |
| 网格线 | `ArenaView.cpp` (第 93-101 行)、`LevelMenuScene.cpp` (第 57-63 行) |
| 角落装饰（corner brackets） | `ArenaView.cpp` (第 129-147 行)、`LevelMenuScene.cpp` (第 66-81 行) |

三组代码逻辑几乎相同，只是常量参数不同（颜色、大小、透明度）。任何一处修改都需要同步到其他文件。

### 3.7 动画中的 this 悬垂引用

**问题：** `GameController` 在创建延时动作时捕获了 `this`：

```cpp
void GameController::onLevelCleared() {
    _scene->runAction(Sequence::create(
        DelayTime::create(2.5f),
        CallFunc::create([this, nextIdx]() { loadLevel(nextIdx); }),  // 捕获 this
        nullptr));
}
```

如果在这 2.5 秒内场景被销毁（例如用户按了返回按钮），`this` 指向的 `GameController` 已被析构，Action 回调触发时产生 use-after-free。

### 3.8 InputController 回调空检查不一致

**问题：** `InputController::onTouchMoved` 和 `onTouchEnded` 调用回调前检查了 `if (_onDrag)` / `if (_onDragEnd)`，但 `onTouchBegan` 没有设置 `setSwallowTouches` 后的条件逻辑问题不大，整体风格不一致。

### 3.9 LevelData 懒加载单例不可重置

**问题：** `getAllLevels()` 使用函数局部 `static` 实现单例：

```cpp
const std::vector<LevelData> &getAllLevels() {
    static auto levels = loadAllLevels();
    return levels;
}
```

一旦加载，无法重新加载。这对单元测试不友好（无法重置状态）——虽然对当前游戏不是问题，但反映了架构上的限制。

### 3.10 AmbientParticles 硬编码调度 Key

**问题：** `AmbientParticles` 使用字符串 `"ambient_spawn"` 作为 schedule key。如果将来有其他组件也用这个 key，会发生静默覆盖。

## 4. 重构建议

按优先级从高到低排列。

### P0 — 安全性修复

#### 4.1 修复 `this` 悬垂引用

在 `GameController` 的延时 Action 中，增加生命周期检查。有两种方案：

**方案 A（推荐）：** 在场景析构时清空所有 Action：

```cpp
GameScene::~GameScene() {
    _scene->stopAllActions();  // 取消所有延时回调
}
```

**方案 B：** 使用 weak 引用机制捕获 `GameController` 的存活状态。但方案 A 更简单可靠。

#### 4.2 修复 VFXHelper 对象池悬挂指针

在场景切换时清理对象池，或对池中的节点进行有效性检查：

```cpp
// 方案：在场景析构时清空池
void VFXHelper::resetParticlePool() {
    for (auto node : g_particlePool.inUse) {
        node->removeFromParent();
    }
    for (auto node : g_particlePool.available) {
        node->removeFromParent();
    }
    g_particlePool.available.clear();
    g_particlePool.inUse.clear();
    g_particlePool.initialized = false;
    // 类似清理 labelPool
}
```

在 `GameScene` 析构时调用：

```cpp
GameScene::~GameScene() {
    VFXHelper::resetParticlePool();
}
```

### P1 — 架构改进

#### 4.3 拆分 GameController

将 `GameController` 按职责拆分为多个独立的 Manager/System：

```
GameController (协调者，大幅精简)
  ├─ LevelManager       关卡加载/切换/生命周期
  ├─ CollisionSystem    碰撞检测分发
  ├─ BallManager        球体创建/销毁/追踪
  └─ VFXCoordinator     VFX 触发（以前在 Controller 中分散调用）
```

每个模块持有自己的状态，`GameController` 仅作为顶层协调者。

#### 4.4 为 GameModel 注入行为

将 `ballCount` 和 `targetsRemaining` 的修改逻辑从 `GameController` 移到 `GameModel`：

```cpp
class GameModel {
    void useBall() { if (_ballCount > 0) _ballCount--; }
    void hitTarget() { if (_targetsRemaining > 0) _targetsRemaining--; }
    bool isCleared() const { return _targetsRemaining <= 0; }
    bool isFailed() const { return _ballCount <= 0 && !isCleared(); }
};
```

而不是在 Controller 中 `_model.setBallCount(...)`。

#### 4.5 抽取重复视觉代码

将背景渐变、网格线、角落装饰抽取为工具函数：

```cpp
// 新文件：common/DrawUtils.h / .cpp
namespace DrawUtils {
    void drawVerticalGradient(DrawNode *node, const Size &size, const Color4F &top, const Color4F &bot, int strips);
    void drawGrid(DrawNode *node, const Size &size, const Color4F &color, float spacing);
    void drawCornerBrackets(DrawNode *node, const Size &size, const Color4F &color, float len, float thick, float pad);
}
```

三个调用者统一使用这些函数，消除重复。

### P2 — 代码质量改进

#### 4.6 统一 View 层模式

当前两种模式并存：
- 命名空间 + 自由函数：`ArenaView`、`BallView`、`TrayView`、`VFXHelper`
- 类：`AimLineView`、`HUD`、`AmbientParticles`

建议统一为：需要内部状态（成员变量）的用类，纯工具函数的用命名空间。当前划分基本合理，但 `AimLineView` 其实完全可以做成命名空间 + 自由函数（它只有一个 `_drawNode` 成员，可以改为每次 `draw()` 时创建）。

#### 4.7 统一 HUD 动画节点的生命周期

将 `showCleared()` / `showFailed()` / `showLevelIntro()` 创建的节点挂到 HUD 自身而不是 `getParent()`：

```cpp
void HUD::showCleared() {
    // 用 HUD 的内容大小而不是父节点大小
    auto parentSize = getContentSize();
    // 节点挂在 this 上
    addChild(flash, 29);
    addChild(cleared, 30);
}
```

如果 HUD 自身大小不够，可以设置 `setContentSize` 或使用 `cocos2d::ProtectedNode`。

#### 4.8 合并 ScoreManager 的倍率计算

确保分数只在 `ScoreManager::addScore` 中计算一次倍率，外部只需取最终结果用于显示：

```cpp
// GameController 匿名命名空间
void applyScoreVFX(Node *parent, ScoreManager &score, int basePoints, const Vec2 &pos) {
    score.addScore(basePoints);  // 内部已处理倍率
    VFXHelper::showFloatingScore(parent, pos, score.score());  // 显示总分或增量和
}
```

或者在 `addScore` 中返回实际增加的分值：

```cpp
int addScore(int basePoints);  // 返回实际增加的分数
```

然后用返回值来显示浮动分数。

### P3 — 低优先级/可选

#### 4.9 LevelData 支持重新加载

为测试需求，增加 `resetAllLevels()` 函数：

```cpp
void resetAllLevels() {
    getAllLevels().clear();  // 但 static 无法被修改
    // 或改用动态初始化的单例
}
```

需要将 `getAllLevels` 改为 non-const 返回或提供 reload 接口。

#### 4.10 Random.h 支持可复现种子

为 `common::rng()` 增加种子设置接口，方便测试：

```cpp
namespace common {
    void setSeed(unsigned int s);
}
```

#### 4.11 AmbientParticles schedule key 改为唯一标识

使用实例指针地址作为 key 的一部分，避免 key 冲突：

```cpp
// 或用 Scheduled 方法绑定到对象生命周期
schedule([this](float dt) { spawnDot(); }, SPAWN_INTERVAL, "ambient_" + std::to_string(reinterpret_cast<uintptr_t>(this)));
```

## 5. 总结

| 优先级 | 问题 | 建议 | 涉及文件 | 预估工作量 |
|--------|------|------|---------|-----------|
| P0 | this 悬垂引用 | stopAllActions | GameController.cpp, GameScene.cpp | 1 处修改 |
| P0 | 对象池悬挂指针 | 增加 reset 函数 | VFXHelper.h/.cpp, GameScene.cpp | 2-3 文件 |
| P1 | GameController 膨胀 | 拆分为多个 Manager | controller/ 下新建 3-4 文件 | 较大重构 |
| P1 | GameModel 贫血 | 移入业务行为 | GameModel.h/.cpp, GameController.cpp | 中 |
| P1 | 重复视觉代码 | 抽取 DrawUtils | 新建文件 + 修改 3 个 View | 中 |
| P2 | HUD 父节点假设 | 改为挂到自身 | HUD.cpp | 3 处修改 |
| P2 | 得分倍率重复 | 统一计算逻辑 | GameController.cpp, ScoreManager.cpp | 1-2 处修改 |
| P2 | View 层模式不统一 | 统一原则 | AimLineView | 小 |
| P3 | LevelData 不可重置 | 增加 reload 接口 | LevelData.cpp | 小 |
| P3 | Random 不可复现 | 增加 setSeed | Random.h | 小 |

P0 项建议在下一迭代中立即修复。P1 项是可选的架构改进，能显著提升长期可维护性。P2/P3 项可根据开发节奏按需执行。
